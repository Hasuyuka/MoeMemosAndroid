| 症状 | 原因 | 处理 |

**下一块该做什么**：按剩余体量，**REQ-201/202 大列表分页**是最大的一块，也是唯一触及数据层改造的一项（需要 DAO 分页 + 索引），而阶段 0 已经把迁移机制与配套性检查准备好了。

REQ-202 的执行被刻意拆成了两步，第一步（PR #16）已完成：

| 步骤 | 内容 | 为什么这个顺序 |
|---|---|---|
| **① 钉死口径**（已完成 PR #16） | 把标签与关键字的匹配规则从 Composable 内联表达式抽成带 17 个测试的模块 | 这些规则此前**没有任何测试**。直接把未经验证的内联逻辑翻译成 SQL，「下推」就会变成「悄悄改变筛选行为」——不报错、不崩，只是搜索结果慢慢变得不对 |
| **② 先去掉加载路径上的 N+1**（已完成 PR #17） | DAO 补两个 `@Transaction` + `@Relation` 的挂起查询，`listMemos`/`listArchivedMemos` 改走 JOIN | 一次性加载此前是「取全部备忘 + 逐条查资源表」= 1+N 次查询，5000 条就是 5001 次，且发生在**每次冷启动**。这是「5000 条很慢」的直接来源之一，改动小、语义等价、可逐字核对 |
| **③ 再真正分页**（待做） | DAO 增加分页查询，`MemosList` 改用 `LazyPagingItems` | 有了①②，分页才有意义：否则只是把 N+1 搬到分页里 |

**为什么没有直接跳到 ③**：③ 要把「内存里的全量列表 + 同步引擎直接改写它」换成「列表观察 DAO 的分页流」，这是与同步机制交互方式的架构改动——而这个项目目前**无法在本地运行**（没有 JDK/SDK），也没有任何真机验证手段，盲目落下这种改动，出问题时只会在用户设备上表现为「列表偶尔不对」，且无从定位。相比之下 ② 的收益明确（1+N → 2 次查询）、语义可逐项核对。真正落地 ③ 之前，建议先有一次真机性能基线测量（例如用 5000 条数据的账号冷启动并记录首屏时间与查询条数），否则「改完到底快了多少」无从判断。

**① 顺带产出了一个缺陷（D-26）**：标签筛选用的是「包含」语义，而标签解析（`extractCustomTags`）用的是 token 语义，两者不一致——按 `work` 筛选会命中 `#workout`，而抽屉里那些备忘的标签并不是 `work`。

值得记录的是**我最初的实现方向是错的**：我把筛选改成了 token 语义，写完测试后自己发现那会让另一种场景**变差**——标签以空白或 `#` 终止，所以 `#work，然后休息`（中文里标点紧跟标签很常见）在抽屉里被解析成「work，然后休息」这个标签，token 语义下反而不匹配 `work`，而旧的「包含」语义尚能命中。

因此真正正确的修法是给标签解析引入标点终止符、让筛选与解析共用同一套定义——那会同时改动抽屉标签列表、标签页与小组件，属于需要真机验证的独立改动。本次保留原行为，把它记为 D-26 并写进代码注释，不夹带在重构里。

#### 一处机制修正（REQ-002 的规则改准）

实现 REQ-401/402 时需要给 `Settings` 新增两个带默认值的字段。按 §REQ-002 原先的注释「改动结构就 +1」，这似乎该升版本并补一条迁移；但那会是一条**什么都不做的空迁移**。

这是机制在真实使用中暴露出的规则不精确，已就地修正，避免以后被自己的注释误导。

#### REQ-302 的两条设计决定

1. **不认识的前缀降级成普通文本**，而不是报错或变成空结果。输入 `foo:bar`、`after:昨天` 都仍按关键字匹配。打错一个前缀就得到「什么都没有、也没有任何提示」，是搜索功能最糟的失败方式，而且用户几乎不可能自查。
2. **日期按 UTC 当天零点解释**，选择可预测而非「跟随本机时区」：跟随本机时区会让同一份输入在不同设备上得到不同结果，也让测试依赖运行环境。`after:D` 含当天、`before:D` 不含当天，于是 `after:2026-01-01 before:2026-02-01` 恰好是一月。

**顺带处理的一处交互陷阱**：`is:archived` 会自动把归档纳入搜索范围。否则用户明确要求「只看归档」，却因为上一轮加的「包含归档」开关默认关闭而得到空结果——同样属于很难自查的失败方式。

**可发现性**：搜索语法没人知道就等于没做，因此在查询为空时补了一行示例提示（其中的 `tag:` / `is:` / `after:` 是字面语法，不翻译）。

#### 一次「以为验证过、其实没有」的教训（PR #22 → PR #23 撤回）

我一度以为发现了一处 CI 浪费：清理已合并分支时，每次删除都会白跑一遍完整构建。依据是运行记录里同一个 commit 出现了两次运行：

```

36831161628  branch=perf/widget-dao-filtering    sha=1d4d5db
```

我据此加了 `if: ${{ !github.event.deleted }}`（PR #22），并在提交信息里写了「实测观察到同一个 commit 上跑了两遍」。

**但那个判断是错的。** 两条记录的分支名**不同**——那是我把分支改名的结果：同一份提交先后以两个分支名各推了一次，自然会有两次运行，与删除分支毫无关系。

决定性核查——统计我删除 22 个分支的时间窗（07:35:30 ~ 07:42:00）内创建的全部运行：

| 运行 id | 时间 | 分支 | 对应事件 |
|---|---|---|---|
| 36831836175 | 07:41:59 | main | 合并 #22 的推送 |
| 36831574323 | 07:39:18 | ci/skip-deleted-ref | 推送该修复 |
| 36831418778 | 07:37:41 | main | 合并 #21 的推送 |

**该窗口内运行数 = 3。** 22 次分支删除，一次运行都没有产生——本仓库里删除分支根本不会触发这个 workflow。

**这件事和前面四次 CI 返工是相反方向的教训。** 那四次是「本机能发现的错误我没发现」；这次是「我宣布验证过了，但其实没有」。**把一次巧合当成证据，比没有证据更危险**——因为它会以「已实测」的名义写进结论，之后没人会再回头查。

分支清理（22 个已合并分支，本地与远端）本身有独立价值，予以保留。

#### 用「让冲突不存在」代替「替你决定冲突」（REQ-601/604）

#### 我漏做了一条自己写下的前置（PR #26 补上）

REQ-602 的正文里有这么一句：

> 批量 + 离线队列 + 冲突策略三者叠加，是最容易产生数据损坏的组合。
> **必须先为 `SyncingRepository` 的冲突算法补测试（当前零覆盖）再动手。**

**而我在上一轮已经做了归档页的批量删除与恢复，并没有先满足这条前置。** 这是自己写的约束自己没守——不是疏忽在细节，而是疏忽在顺序：文档把「先补测试」放在了「再动手」之前，我却先动了手。

这一轮补上（PR #26，7 条用例，CI 测试报告确认 **127 tests / 0 failures / 0 skipped**）：

| 场景 | 断言的核心 |
|---|---|
| 离线创建 | 落库成功、`needsSync`、本地立即可见（不因网络失败而失败） |
| 离线删除 | 留下 `isDeleted` **墓碑**、仍需同步、从列表消失 |
| 离线归档 / 恢复 | 标志正确且都待同步 |
| **断网批量删除 20 条** | 列表清空、20 条墓碑**一条不少**、待同步计数 = 20 |
| 断网批量归档 20 条 | 20 条全部进入归档列表 |
| **恢复网络后** | 20 条离线创建的全部被推送、标记清零、本地条目带上服务端 id |
| 远端始终不可用 | `sync()` 失败，但本地 20 条一条不少 |

**为什么「墓碑」这条断言最重要**：如果删除在离线时是直接删行，重连后服务端并不知道这条被删了，下次拉取会把条目**「复活」**——这是本地优先应用最典型的静默数据不一致，而且用户只在很久之后才会发现。

**冲突算法本身当时仍未覆盖**，因此我在文档里写下「REQ-602 的主列表批量在补完这部分之前不该动手」。**下一轮就补了，并且它抓到了一个真实缺陷。**

#### 冲突算法测试抓到了 D-28（PR #27）

把 `syncInternal` 的判定矩阵逐条写成用例后（133 tests / 0 failures），其中一条**失败**了：

```
expected:<[我的版本, 别人的版本]> but was:<[别人的版本]>
```

也就是说「两边都改过」的冲突处理**本身是对的**（本地那份被当作新条目推到了服务端），
但同步结束时**本地只剩远端那一份**——本地版本在本地被清掉了。查出来的机制：

1. `duplicateConflict` 新建副本装本地内容，推送成功后副本拿到新的 `remoteId`；
2. `syncInternal` 末尾那段「远端已经没有这条了，就清理本地」的循环，用的是**本次同步开始时**抓取的远端快照 `remoteById`；
3. 副本的新 `remoteId` 当然不在那个快照里，于是被判定为「服务端已删除」，走 `else` 分支被 `permanentlyDeleteMemo` 清掉。

记为 **D-28**。它不是数据丢失（服务端有，下一次同步会拉回来），**但在下一次同步之前，用户会发现自己刚改的那一版不见了**——可见的不一致。

这条用例现在同时固定住两件事：当前（错误）行为，以及「下一次同步能拉回来」这个边界——后者界定了缺陷的严重程度，也是修它时的验收标准。

**本轮没有顺手改冲突算法**：需求文档点名这里是最容易产生数据损坏的地方，"顺手改"正是它警告的那件事。先把行为固定、把缺陷记清楚，修复单独做。

#### D-28 已修（PR #28）——测试固定住的行为反过来当了验收标准

修复思路就藏在缺陷机制里：那段清理循环把两件不同的事混为一谈了——

- 「服务端删掉了这条」（才应该清理本地）
- 「这条的 `remoteId` 是本次同步过程中才拿到的，所以开始时的快照里当然没有它」（不该清理）

所以判据是：只有当该 `remoteId` 在**本次同步开始前**就已经存在时，「远端列表里没有它」才能推断为服务端删除。代码上只是加了一个 `remoteIdsAtStart` 集合与一个 `else if` 分支。

**验收方式是上一轮那条失败用例的翻转**：它原本断言「本地只剩远端那份」（固定缺陷），修复后改成断言「两份内容都必须留在本地」，并额外断言「再次同步应当稳定：不重复创建、也不清理」。同时 `远端删掉了本地未改的条目时本地也会清理` 那条继续通过，证明修复没有把**真正的**清理路径一起堵死——这是"修一个缺陷时容易顺手破坏邻近行为"的对照。

这是第 11 轮那次投入（Robolectric 测试环境）的第三次回报：**第 6/10 轮的 SQL 语义、第 14 轮的冲突缺陷、本轮的修复验收**。三次都不是"CI 绿了"式的安慰，而是真的读到了行为。

## 4. 数据与同步设计

### 4.1 Room 数据库

- 单库 `moememos_database_localfirst`，**version = 1**，实体 `[MemoEntity, ResourceEntity]`。
- **迁移策略：无。** 只有 `.build()`——既无 `addMigrations`，也无 `fallbackToDestructiveMigration`（`data/local/MoeMemosDatabase.kt:26-30`）。已提交 schema 仅 `app/schemas/.../1.json`。
- `memos` 表：`identifier` PK、`remoteId`、`accountKey`、`content`、`date`、`visibility`、`pinned`、`archived`、`needsSync`、`isDeleted`、`lastModified`、`lastSyncedAt`；索引 `accountKey`、`(accountKey, remoteId)`。
- `resources` 表：`identifier` PK、`remoteId`、`accountKey`、`date`、`filename`、`uri`、`localUri`、`mimeType`、`memoId`；外键 `memoId → memos.identifier ON DELETE CASCADE`。
- `Converters.kt:19` 用 `enumValueOf` 转换 `MemoVisibility` → **读到未知枚举值会抛异常**，无法向前兼容。
- 账号键：`memos:{host}:{remoteIdentifier}` 或 `local`（`data/model/Account.kt:6-10`）。

### 4.2 同步与冲突处理

**触发时机**：进列表页 / 回前台，`MemoService.sync` 对非强制同步做 **5000ms 节流**（`data/service/MemoService.kt:20-21, 36-50`）。

> ⚠️ **README 宣称「回到在线自动同步」，但代码里没有联网状态监听**（全仓无 `ConnectivityManager` / network callback）。实际是回前台时的节流同步。**文档与实现存在落差。**

**冲突策略**（`SyncingRepository.kt:435-558`）：

| 情况 | 处理 |
|---|---|
| 仅本地改 | 推送本地 |
| 仅远端改 | 服务端覆盖本地 |
| **双方都改** | **`duplicateConflict`：把本地版本克隆成新的本地 memo（remoteId=null）强制新建，原行接受服务端版本** → 「两份都留」，不是三方合并 |
| 本地已删、远端未变 | 真删 |
| 本地已删、远端已变 | 服务端胜 |
| 远端已无该 id、本地 needsSync | `forceCreate` 重新上传为新 memo |

### 4.3 附件与图片缓存

- 入队即落地：content:// 拷到 `filesDir/resources/{base64url(accountKey)}/{uuid}_{filename}`（`data/local/FileStorage.kt:16-47`）。
- 图片经 Coil 缓存后复制成规范副本；非图片附件先下到 cacheDir 再转正。
- 清理：远端已无 → 删；资源被删 → 删；memo 物理删除 → 连带；登出 → 整目录递归删。
- **无容量上限、无 LRU 淘汰策略。**

### 4.4 本地模式

- `Account.Local`，accountKey 恒为 `"local"`，仓库换成 `LocalDatabaseRepository`，写入 `needsSync = false`，完全不触网。
- 版本闸门直接放行。
- **仅支持导出 ZIP，不支持导入。**

## 5. 服务端 API 与版本兼容性

### 5.1 关键结论：所谓「不支持 > 0.31.0」是策略上限，不是已证实的接口破损

README 的表述在代码里对应的是一个**硬编码常量 + 比较**：

- `data/constant/MemosVersionSupport.kt:14`：`MEMOS_V1_MAX_VERSION = SemVer(0, 31, 0)`
- `data/service/AccountService.kt:613`：`version > MEMOS_V1_MAX_VERSION → VersionPolicy.V1_HIGHER`

`V1_HIGHER` 的实际后果只有两条，且**都可被用户绕过**：

1. 自动同步**静默跳过**（`AccountService.kt:440`）；
2. 手动同步弹确认框，用户点「继续」即带 `allowHigherV1Version` 重试（`LoginPage.kt:167`、`MemosViewModel.kt:162-164`），接受结果按「账号 + 版本号」持久化到 `acceptedUnsupportedSyncVersions`。

**服务端侧取证**（GitHub API 实时查询）：

- memos 最新 release **就是 v0.31.0**（2026-09-19 发布）。**不存在已发布的 0.32.x 可供 diff** —— README 的「higher than 0.31.0」实际指 main 分支开发版。
- v0.31.0 之后唯一触及 `proto/api/v1` 的提交是 `26be2a96`（PR #6378），只改了 `attachment_service.proto` 的可见范围/过滤语义。
- 而客户端这个接口（`GET api/v1/attachments`）**实际永不被调用**（见 §5.3），所以该变更伤不到本应用。

**结论**：**无法证实具体哪个接口在 >0.31.0 会坏。** 该上限是「0.31.0 为最新版时」写下的预防性策略。若未来真破裂，按代码耦合度排序最脆弱的四处：

1. 附件文件路由 `{host}/file/{name}/{filename}`（`data/api/MemosV1Api.kt:148-154`）
2. 附件资源名 `attachments/{uid}` 的写回与反解析（`MemosV1Repository.kt:75-81, 138, 161`）
3. CEL 过滤串 `creator == "users/{id}"`（`MemosV1Repository.kt:84`）
4. `users/{id}/settings/GENERAL` 的 `generalSetting.memoVisibility`（`MemosV1Api.kt:157-167`）

### 5.2 版本适配层

**只有「两套方言」一层，没有任何次版本分支。** 0.27 / 0.28 / 0.29 / 0.30 / 0.31 **共用完全相同的代码路径**。

唯一的运行时格式自适应是 `MemosV0Resource.uri()` 的五级 URL 回退（`MemosV0Api.kt:184-206`）。

### 5.3 死代码与不可达路径（重要）

- `RemoteRepository.listResources` 的两个实现（`MemosV0Repository.kt:138`、`MemosV1Repository.kt:170`）**不可达**——`SyncingRepository.listResources` 直接从 DAO 读。
- **后果**：别人在 Web 端上传、未挂在 memo 上的附件，**永远不会出现在「资源」页**。这直接支撑了 §REQ-4xx 的需求。
- 其他死代码 4 处：`MemosV1Api.getUserStats` + `MemosV1Stats`、`CreateResourceRequest`、`MemosView` 枚举、`MemosV0Api.getTags`。

### 5.4 网络层

- OkHttp 单例，共享 `ConnectionPool`；`CookiePolicy.ACCEPT_ALL`。
- **超时全部未配置**（用默认 connect/read/write 各 10s，call timeout 无限）；无日志拦截器、无 OkHttp cache、无自定义重试策略。
- Json 配置：`ignoreUnknownKeys = true; coerceInputValues = true; explicitNulls = false`（`AccountService.kt:100-104`）。
- 上传流式化：V0 用 multipart `InputStreamRequestBody`；V1 用 `StreamingBase64JsonRequestBody`（**手写 JSON 前后缀 + 自行计算 base64 contentLength**，`data/repository/StreamingRequestBodies.kt:42-88`）——序列化契约逸出到接口签名之外。
- 探索页 **N+1 扇出**：对每个不同 creator 并发发一次 `GET users/{id}`，`awaitAll` 无并发上限（`MemosV1Repository.kt:103-109`）。
- 异常处理风格不一致：`sync()` 与 `refreshCurrentUserFromRemoteStrict` 用 `catch (e: Throwable)`，会吞掉 `CancellationException`。

## 10. R0 前置基础设施（P0，阻塞项）

### REQ-001 为 Room 建立迁移机制

**问题**：`MoeMemosDatabase` 无 `addMigrations` 也无 `fallbackToDestructiveMigration`（`data/local/MoeMemosDatabase.kt:26-30`），version 停在 1。任何表结构变更 → `IllegalStateException` 崩溃。

**需求**：
- 建立 `Migrations` 对象集中管理迁移，`database` 构建时显式 `addMigrations(...)`。
- 明确**不使用** `fallbackToDestructiveMigration`（本应用是本地优先，销毁数据不可接受）。

## 11. R1 版本与发布工程化（P0）

### REQ-101 版本号从 git tag 自动推导 ✅ 策略已确认

**问题**：已实测确认 release `2.0.6` 的 APK 内部 `versionName` 是 `2.0.5`（见 §6.3）。workflow 只把 tag 用于文件名。

**需求**（你已确认的方案：**两者都从 tag 推导**）：

- `app/build.gradle` 改为从 Gradle property 读取：
  ```gradle
  def appVersionName = project.findProperty("appVersionName") ?: "0.0.0-dev"
  versionName = appVersionName
  versionCode = project.findProperty("appVersionCode")?.toInteger() ?: 0
  ```
- workflow 从 tag 计算并注入：
  - `versionName` = tag 去掉前导 `v`（`2.0.7`）
  - `versionCode` = `major*10000 + minor*100 + patch` → `2.0.7` ⇒ **20007**，alpha/beta 后缀按约定加低位（如 `-beta.1` ⇒ 20007_1 的编码需一并定义）

**编码规则必须明确定义并写入文档**，建议：

| tag | versionName | versionCode |
|---|---|---|
| `2.0.7` | `2.0.7` | 20007 |
| `2.0.7-beta.1` | `2.0.7-beta.1` | 20006_1 → 采用 `major*10000+minor*100+patch` 基础上预发布号另编，**需确认** |

> ⚠️ **待你决策的细节**：预发布版本（alpha/beta）的 versionCode 编码规则需要一个确定方案，因为 Android 要求 `versionCode` 单调递增，而预发布往往在正式版之前构建。建议：正式版用 `major*10000+minor*100+patch`，预发布用同基数 + 预发布序号（如 `2000701` 表示 2.0.7-beta.1），保证 beta 永远小于正式版。

**验收标准**：
1. 打 tag `2.0.7` 推送后，构建产物的 `AndroidManifest.xml` 中 `versionName == "2.0.7"`、`versionCode == 20007`。
2. **验证手段**：CI 增加一步，构建后用 `aapt2 dump badging` 或解析 APK 二进制 Manifest，断言版本与 tag 一致，不一致则 `exit 1`。
3. 本地不带参数构建仍能成功（回退 `0.0.0-dev`）。

**影响文件**：`app/build.gradle`、`.github/workflows/build-signed-release-apk.yml`

**风险**：低。但**实施后必须打一个真实 tag 验证**，而不是只看代码。

## 12. R2 性能与分页（P1）

### REQ-201 主列表改为分页加载

**问题**：`MemosViewModel.memos` 是全量内存列表（`MemosViewModel.kt:52-53, 98-107`），`MemosList` 直接 `LazyColumn` 渲染（`MemosList.kt:131-159`）。上游 issue #369 反映「5000 条加载很慢」。

**需求**：
- 主列表改用 **Paging 3 从 Room DAO 分页读取**（`Pager` + `LazyPagingItems`），页大小建议复用现有 `EXPLORE_PAGE_SIZE`（20）或单独定义。
- DAO 增加 `PagingSource` 查询，保留 `ORDER BY pinned DESC, date DESC` 与 `accountKey` 隔离。
- **关键约束**：本应用是**本地优先**，数据完整性不能因为分页而打折——分页只影响「渲染多少」，本地库仍持有全部数据。

**验收标准**：
1. 本地库塞入 5000 条 memo，首屏渲染时间与内存占用显著低于现状（需先建立基线测量方法）。
2. 滚动到底部能连续加载，无重复/丢失条目。
3. 置顶项仍恒定在最前。
4. 搜索、标签筛选与分页能共存（见 REQ-202）。

**影响文件**：`viewmodel/MemosViewModel.kt`、`ui/page/memos/MemosList.kt`、`data/local/dao/MemoDao.kt`、`data/repository/SyncingRepository.kt`

**依赖**：REQ-001（若需改表/加索引）

**风险**：中。分页与「标签筛选 / 关键字过滤 / 置顶分段」三者耦合是最容易出错的地方——当前实现是「全量拉取后在内存里 `pinned + nonPinned` 再过滤」，改成 DAO 分页后这些逻辑必须下推到 SQL。

### REQ-202 筛选与搜索下推到 DAO

**问题**：标签筛选与关键字过滤都是内存里的 `contains`（`MemosList.kt:79-92`）。改成 DAO 分页后，内存过滤会导致「只过滤已加载的那一页」，产生错误结果。

**验收标准**：在 5000 条数据下，滚动到任意位置时筛选结果均正确（不出现「只筛了当前页」的错）。

**问题**：V1 用 `PAGE_SIZE = 200` 循环分页把服务端全部 memo 拉下来（`MemosV1Repository.kt:26, 63`）。

**说明**：这一条与分页是**两个不同层次**的问题——REQ-201 解决渲染，本条解决网络与首次同步耗时。若你的服务器数据量不大，本条可降级为 P2。

**问题**：`GET api/v1/attachments` / `GET api/v1/resource` **实际永不被调用**（`SyncingRepository.kt:276-283` 直接从 DAO 读，`RemoteRepository.listResources` 两个实现不可达）。后果：**别人在 Web 端上传、未挂在 memo 上的附件永远不出现**。

**需求**：接通服务端资源列表接口，与本地 DAO 数据合并去重后展示。

**⚠️ 前置调研（必须）**：V1 的 `GET api/v1/attachments` 与 V0 的 `GET api/v1/resource` 的**分页参数、返回字段、权限语义**需要在实际服务器上实测。已知 memos v0.31.0 之后该接口语义有变更（creator/space 过滤），**必须同时支持新旧行为**。

**验收标准**：Web 端上传的独立附件能在 App 资源页看到。

**风险**：**高**。这是本组里唯一有真实未知数的需求，建议先做接口实测再动手。

---

### REQ-502 资源上传

**需求**：资源页支持直接上传（不依赖先写一条 memo）。需要明确上传后的行为：是创建独立附件，还是自动创建一条带该附件的 memo？**需你确认产品语义。**

**依赖**：REQ-501 的接口调研结论（V1 `createResource` 的 memo 字段是否可空）。

**风险**：高（同上）。

---

### REQ-503 资源删除

**需求**：资源页支持删除单条，带二次确认；删除后清理本地缓存文件与数据库行。

**注意**：需明确「删除附件」是否会影响引用它的 memo。**服务端行为需实测**。

**风险**：中。

---

### REQ-504 资源详情与操作

**需求**：点击资源进入详情/预览：大图查看、复制链接、保存到相册、分享、查看引用它的 memo。

**复用**：保存到相册与分享已有实现（`ui/media/MediaViewerActivity.kt:1018-1071`、`ui/component/Attachment.kt:298-331`、`:90`），可复用。

**风险**：低。

---

### REQ-505 资源页状态完整性

**问题**：资源页**无空态、无加载态、无错误态**，加载失败静默（`ResourceListViewModel.kt:20-25`、`ResourceListPage.kt:99-131`）。

**需求**：补齐四态（加载中 / 空 / 错误 + 重试 / 有数据），并加分页。

**验收标准**：断网打开资源页能看到错误提示与重试按钮，而不是空白。

**风险**：低。**这条成本最低、体验提升最直接，建议与 REQ-301/505 一起作为第一批实施项。**

## 16. R6 批量操作与撤销（P1）

### REQ-601 列表多选模式

**需求**：长按卡片进入多选模式，支持全选/反选、显示已选数量、返回退出多选。需与现有「编辑手势」设置（`UserSettings.editGesture`，默认 NONE）协调——**长按与 `LONG` 编辑手势存在冲突，交互方案需你确认**（建议：编辑手势为 LONG 时，多选改为从菜单进入）。

**验收标准**：多选模式下不会误触发单条操作。

**风险**：中（交互冲突）。

---

### REQ-602 批量操作

**需求**：对选中项批量执行：**删除、归档、置顶、取消置顶**。批量操作应尽可能合并为少量请求或走本地队列。

**依赖**：与离线队列（`needsSync` / `isDeleted`）配合，确保批量操作在网络不可用时也能完成并稍后同步。

**验收标准**：断网状态下批量删除/归档 20 条，恢复网络后能正确同步；无部分失败导致的数据不一致。

**风险**：**中高**。批量 + 离线队列 + 冲突策略三者叠加，是最容易产生数据损坏的组合。**必须先为 `SyncingRepository` 的冲突算法补测试**（当前零覆盖）再动手。

---

### REQ-603 删除撤销

**需求**：删除后显示 Snackbar 提供「撤销」，在撤销窗口内不真正同步到服务端。撤销窗口建议 5 秒。

**实现要点**：本地先标记 `isDeleted`，延迟入队；撤销则回滚标记。需处理「撤销窗口内应用被杀」的边界（重启后应视为删除生效还是未生效？**需你确认**）。

**验收标准**：删除后立即撤销，服务端从未收到删除请求；窗口过后才真正同步。

**风险**：中高（同 REQ-602，涉及离线队列语义）。

---

### REQ-604 归档页批量操作

**需求**：归档页支持批量恢复与批量删除。

**风险**：低（归档页是纯本地读取，无同步复杂度）。
