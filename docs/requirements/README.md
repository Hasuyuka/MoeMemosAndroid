# 需求条目怎么写

## 一条需求 = 一个文件

```
docs/requirements/R-<三位序号>-<短标题>.md
```

例子：`R-007-按标签批量移动.md`

**不要**把所有需求塞进一个大文档。理由很实际：一个大文档在 git 里没法评审、
没法只回滚一条、也看不出哪条改过。

> 历史上那份 `需求文档-MoeMemos.md`（1068 行）已经移到
> [`00-baseline-2026-10-01.md`](00-baseline-2026-10-01.md) 存档。
> 它是 fork 初期的代码梳理 + 需求草稿，**不要往里面加新内容**，
> 新需求按上面的命名另开文件。

## 状态机

需求文件头部的 `状态` 只有这五个值，含义固定：

| 状态 | 含义 | 谁能改 |
| --- | --- | --- |
| `草案` | 在写，验收标准可能还不全 | 需求作者 |
| `待评审` | 写完了，等确认范围与优先级 | 需求作者 |
| `已确认` | 范围、验收标准都定了，可以开工 | 决策人 |
| `实施中` | 有对应分支/PR 了 | 开发 |
| `已完成` | 验收标准全部通过，且已发版 | 开发 |

`草案` / `待评审` 的需求**不要开工**。返工的成本远高于多问一句。

## 优先级

| 级别 | 含义 |
| --- | --- |
| `P0` | 不做就没法用（崩溃、丢数据、核心流程断了） |
| `P1` | 核心体验，近期必做 |
| `P2` | 增强，有空再做 |

丢数据类的 bug 一律 `P0`，哪怕"只影响一个很少用的按钮"。

## 验收标准的写法

**好**的验收标准长这样：

- `AC-1`：给已有备忘追加 1 张图片并保存后，该备忘的图片附件数 = 原有数 + 1。
- `AC-2`：上述操作后，原有的每一张图片都仍能正常显示。
- `AC-3`：断网状态下重复上面的操作，结果相同。

**坏**的验收标准长这样：

- ~~保存图片时要正确~~（没有可判定的结果）
- ~~体验要流畅~~（不可测，除非给出具体指标）

判断标准：**换一个人拿到这条 AC，能不能独立判断通过还是失败？** 不能就重写。

## 哪些 AC 必须落成测试

按能否自动化分三类，写在需求文件的「验证方式」一节：

1. **逻辑可测** → 必须写单元测试（纯函数、DAO、状态机）。
   CI 每次跑，回归时立刻发现。
2. **界面可测** → 尽量写 Compose/Robolectric 测试；做不到就靠真机验证并留下截图。
3. **只能人眼判断** → 写明"由人工在真机确认"，并附上判断依据（例如"间距不是
   一条大沟"）。

第 3 类不是偷懒的借口。这次修附件丢失时，界面上那三个空白格子本身是"看起来像
渲染 bug"的，真正的证据是文件系统里 `ENOENT` —— 那种东西必须进第 1 类。
