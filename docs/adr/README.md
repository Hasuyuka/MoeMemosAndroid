# 架构决策记录（ADR）

## 什么时候写

满足下面**任意一条**就该写一条 ADR：

- 有两个以上都说得通的方案，我们选了其中一个；
- 这个决定以后想改，成本不小（改了要动数据结构、动多个页面、要迁移）；
- 这个决定曾经被推翻过，以后可能有人（包括未来的自己）想再推翻一次。

**不需要**写 ADR 的：改个文案、修个明显的 bug、加一个独立的小功能。

## 为什么值得写

这个项目里最贵的一课，是"滚动位置丢失"那一轮：

前后发了 **8 个 beta 版本**才定位到根因，其中三个版本是在互相推翻——
beta.12 把 beta.11 的规则放宽，结果更糟；beta.13 又撤回。每一版都只留下一个
commit message，没有留下"当时为什么这么判断"。

如果第一版就写了 ADR，写着写着就会发现"我没有证据证明位置丢失发生在哪一步"，
那个问题会在写文档时暴露，而不是在真机上暴露三次。

## 格式

文件名：`ADR-<三位序号>-<短标题>.md`，一条决策一个文件，**写完之后不再修改正文**。
后来推翻了就新写一条，在旧的那条顶部加一行 `> 已被 ADR-xxx 取代`。

正文包含：背景现状 / 备选方案与取舍 / 决定 / 后果与代价 / 验证方式。
