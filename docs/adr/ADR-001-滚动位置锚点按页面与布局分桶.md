# ADR-001：滚动位置锚点按「页面 + 布局」分桶

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-10-06 |
| 状态 | 已采纳 |
| 相关需求 | 灵感页/标签页滚动到中间后点开备忘，返回时应回到原处 |
| 相关代码 | `viewmodel/MemosViewModel.kt`、`ui/page/memos/MemosList.kt` |

## 背景

返回列表后位置丢失，这个现象前前后后发了 **8 个 beta 版本**才收敛。最后真机埋点
给出的事实是两条，都不是"锚点没记对"：

1. **列表页的滚动位置其实没丢。** 埋点里新组合的第一帧 `fv=9:548` ——
   `rememberLazyListState` 经由 `SaveableStateHolder` 正常恢复了。
   之前 5 个版本的锚点补丁从一开始就没打在要害上。
2. **真正的原因是列表在返回后被重排了一次。** 具体是设置读取用了编造的默认值
   （`Settings()`），导致首帧按默认排序 `CREATED` 渲染，第二帧才换成用户的
   `TITLE`；同一 memo 的 index 从 66 跳到 22，用户看到的就是"随机跳到某处"。

在定位到 2 之前，锚点机制本身还有一个独立缺陷：锚点里带 `layout` 字段，
布局一变恢复就整体作废，而"回顶"照跑，于是切到网格必然落回顶部。

## 备选方案

**方案 A：维持单个全局锚点字段（原状）**
三页共用、两种布局共用。恢复时比对 `layout` 决定要不要恢复。
→ 否决。它让"布局切换"和"换页面"都变成"锚点作废 → 停在顶部"。

**方案 B：按「页面 + 布局」分桶（已采纳）**
`Map<String, MemoScrollAnchor>`，key = `页面标识|布局名`。
→ 采纳。三页之间、大卡片与网格之间互不覆盖；切换布局变成"恢复该布局自己
上次的位置"，而不是"作废 + 回顶"。

**方案 C：把 `LazyListState` / `LazyGridState` 提到 pane scaffold 之上**
让滚动状态根本不随列表面板销毁，从根上不需要锚点。
→ 暂缓。改动面大（要穿过 `MemoBrowser` 的 listPane lambda 传下去），
而当时更需要的是先止血。**如果以后发现锚点方案还有漏网场景，这个方案值得重新评估。**

## 决定

采用方案 B，同时：

- 「回到顶部」只在**布局真的换了**时才执行（用 ViewModel 里的
  `lastSeenLayouts` 判断，不能用 `LaunchedEffect(layout)` —— 那个 key 只管同一次
  组合内的重启，列表页每次被重新组合都会无条件跑一次 `scrollToItem(0)`）；
- 回顶时**顺手清掉该布局的锚点**，否则紧接着启动的恢复副作用会把刚滚到的顶部
  又拉回去，两个副作用互相打架。

## 后果与代价

- 好处：切布局不再丢位置；三页之间不再互相污染。
- 代价：锚点从"一个字段"变成"一张表"，key 由页面标识（`tag=…` / `q=…` / `memos`）
  和布局名拼成，**新增列表页时必须同时在 `MemosList` 里把它加进 `pageKey` 的推导**，
  否则会和灵感页共用一个桶。
- 遗留：方案 C 没做。列表面板被销毁时仍然依赖锚点恢复，而不是状态本身存活。

## 验证方式

- 真机手动：滚到中间 → 点开一条 → 返回 → 首个可见备忘应与点开前一致。
  已在 `YAL-AL00`（Android 10）上用 13 条备忘验证：返回前后首个可见项都是
  `memo9`，纵向偏移 354 → 312（42px 轻微偏移，不是跳顶）。
- 切布局：大卡片 ↔ 两列 ↔ 三列，各自回到自己上次的位置。
- 回归测试：`planMemoListUpdate` 的 `resources` 变更检测有单元测试；
  滚动位置本身目前只有人工验证（见 [`../testing.md`](../testing.md) 的待办）。
